# Contributing to AIBrix NeoCloud Node

Thanks for your interest in AIBrix NeoCloud Node. The project is experimental,
so the best contributions are small, well-scoped fixes that improve reliability,
provider compatibility, tests, and documentation.

## Development Setup

Install Go 1.26.11 or newer and Kustomize 5.4 or newer, then run the same verification suite
used by CI before sending changes:

```bash
make verify
make test-race
```

`make vulncheck` runs a strict local vulnerability scan and exits nonzero on
findings or scanner errors. In the regular CI workflow, vulnerability scanning
runs as an independent advisory job: findings and scanner failures remain visible
in logs, warnings, and the job summary, but do not block PR checks or main-branch
commit-image publication. Do not configure the advisory job as a required branch
check. Version-tag releases retain a blocking vulnerability scan.

For credential-free lifecycle testing, follow the
[Fake Provider walkthrough](docs/development.md#fake-provider). See
[container images](docs/development.md#container-images) for published tags
and running a development build.

Use `make docker-build` to build the runtime image. Kubernetes deployment bases
live under `config/`; `deploy/neocloud-node.yaml` is generated by
`make manifests` and must be committed whenever a base changes.

The real RunPod, Lambda Cloud, and Vast.ai smoke tests are gated because they
create paid cloud resources. Do not run them unless you have an account, a
cleanup plan, and the required environment variables set. See the
[development guide](docs/development.md) for commands and defaults.

## Contribution Guidelines

- Keep provider-specific behavior inside the provider adapter packages.
- Keep Kubernetes API access in the Virtual Kubelet/provider wrapper and binding
  store layers.
- Do not silently ignore unsupported Pod fields. Return a clear unsupported
  reason and surface it through status or events.
- Preserve idempotency. A controller restart or provider retry must not create
  duplicate paid resources for the same Pod UID.
- Add or update tests for lifecycle, transformation, provider error
  classification, and cleanup behavior.
- Keep RBAC least-privileged. Add a verb only when a concrete controller call
  requires it, and cover the change in the manifest tests.
- Never commit provider API keys, cloud credentials, cloud or provider logs,
  local trace outputs, or paid resource identifiers.

## Local Secret Scanning

Before each commit, stage the intended changes and scan them locally. Install
[Gitleaks](https://github.com/gitleaks/gitleaks#installing) using its official
instructions, then run from the repository root:

```bash
gitleaks git --staged --redact
git diff --cached
```

Review the staged diff manually as well: scanners may miss cloud logs, provider
keys, and paid resource identifiers. Use clearly fake placeholders in examples
and fixtures. Fix findings, stage the corrected files, and rerun the scan before
committing. Repeat after further edits and before opening a pull request; if
changes are already committed, `gitleaks git --redact` scans local Git history.

If a real credential was committed, revoke or rotate it immediately and remove
it from the affected commits before pushing. If it was already pushed, notify
the maintainers privately so they can coordinate cleanup. Never paste the secret
or unsanitized logs into an issue or pull request.

## Self-assigning an issue or pull request

Any contributor can claim an open issue or pull request by commenting `/assign` on it.
The repository's assign workflow adds you as an assignee:

- Comment `/assign` on an issue or pull request to assign it to yourself. The command
  works on both issues and pull requests.
- It is safe to repeat `/assign`; assigning an already-assigned user is a no-op.
- Only comment `/assign` when you plan to work on the item soon. If you become
  unavailable, ask a maintainer to unassign or reassign it so others can pick it up.
- Maintainers may change assignees at any time.

## Good First Areas

- Documentation consistency and examples.
- Additional deployment overlays and packaging.
- Provider metrics and orphan sweeper events.
- RunPod logs or provider console links.
- Lambda runner heartbeat timeout and diagnostics.
- More provider contract tests against fake HTTP servers.
